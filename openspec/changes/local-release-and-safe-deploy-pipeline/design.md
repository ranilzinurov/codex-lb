# Проектирование локального выпуска и безопасного развёртывания

## Поток данных

```text
published commit SHA
        |
        v
clean detached worktree -> selected validation -> buildx --push linux/amd64
                                                       |
                                                       v
                                             GHCR image digest
                                                       |
                                  revision + security gate + manifest
                                                       |
                                                       v
                                              deploy doctor
                                                       |
                                                       v
                                      backup -> deploy -> fingerprint
                                                       |
                                             ready or rollback
```

Digest — единственный идентификатор, передаваемый между публикацией и
развёртыванием. Тег по SHA удобен для поиска, но не является контрактом запуска.

## Решение 1: отдельный локальный оркестратор выпуска

Оркестратор предоставляет одну команду верхнего уровня и небольшие отдельно
тестируемые функции: проверка Git, выбор набора проверок, подготовка worktree,
вызов buildx, разбор digest, проверка revision, запуск сканера и запись
манифеста. Команда должна поддерживать режим предварительной диагностики без
публикации.

Сборка выполняется только из detached worktree выбранного SHA. Исходная рабочая
копия может содержать пользовательские изменения, но они не входят в образ;
если пользователь пытается выпустить текущий грязный `HEAD`, команда явно
отказывает. SHA должен существовать в настроенном удалённом репозитории форка.

Buildx получает `--platform linux/amd64` и `--push`. Кэш хранится локально либо
в выделенном реестровом namespace и не влияет на итоговый digest. Для Docker
используется временный `DOCKER_CONFIG`, который удаляется в блоке завершения.

После публикации оркестратор разрешает registry digest и сверяет OCI-метку
revision с выбранным SHA. Один контроль безопасности запускается над
опубликованным digest; дублировать сканирование до и после push не требуется.
Готовый манифест имеет версионированную JSON-схему и содержит только
несекретные сведения и результаты ворот.

## Решение 2: два уровня проверок и замороженный SHA

`fork-contract` объединяет быстрые проверки собственных точек расширения,
критичных конфигурационных контрактов и затронутых модулей. Полный набор
запускается, когда изменены зависимости, миграции, Docker/runtime, общие
контракты либо перенесены upstream-изменения. Явный параметр всегда может
повысить уровень до полного, но не понизить автоматически обязательный полный
уровень.

Локальный выпуск проверяет, что успешный результат относится к тому же SHA.
Во время проверки он не подтягивает upstream и не меняет ветку. Любое исправление
создаёт новый SHA и новый кандидат.

GitHub Actions использует те же области изменений на pull request, push в
`main` и merge queue. Обязательные контексты создаются всегда; ненужные дорогие
команды заменяются успешными placeholder-шагами. Полный набор доступен через
явный `workflow_dispatch` и автоматически включается для изменений областей,
которые требуют его по контракту.

## Решение 3: ограниченный параллелизм Vitest

Начальная настройка полного frontend-набора — не более двух работников.
Тестовые файлы должны владеть своим MSW-состоянием, таймерами и хранилищем.
Наборы, которые невозможно безопасно изолировать в рамках этой работы,
выделяются в именованную последовательную группу. Перед включением конфигурация
проходит несколько повторных полных прогонов; единичное ускорение не считается
достаточным доказательством стабильности.

Порог времени не встраивается как жёсткий тест, поскольку скорость runner-ов
нестабильна. В PR фиксируются сравнимые замеры, число работников и перечень
оставшихся последовательных наборов.

## Решение 4: `deploy doctor` и безопасное освобождение места

`doctor` переиспользует разбор конфигурации и проверки deploy-модуля, но не
останавливает контейнеры, не удаляет образы и не меняет state-файл. Результат
доступен человеку и в JSON, чтобы локальный оркестратор мог остановиться до
начала окна обновления.

Перед основной проверкой свободного места deploy может удалить только образы,
которые больше не являются:

- запущенным/активным образом;
- новым кандидатом;
- единственным предыдущим образом, пригодным для отката.

Идентификаторы сравниваются как полные digest/ID, а не сокращённые префиксы.
Если безопасной очистки недостаточно, deploy завершается до остановки сервиса.

## Решение 5: отпечаток состояния как контракт сохранности

До обновления и после готовности создаётся JSON-отпечаток непубличных значений,
не раскрывающий секреты. Он включает стабильные идентификаторы хранилища,
количество основных записей и необратимые хэши выбранных значений конфигурации.
Набор полей версионируется, чтобы сравнение было воспроизводимым.

Допустимые монотонные изменения, возникающие от фоновой работы между двумя
снимками, задаются явно. Исчезновение записей, смена каталога/базы либо изменение
хэшей защищённых API-ключей и токенов является ошибкой и вызывает откат. Сами
значения ключей никогда не выводятся.

## Решение 6: настоящий Docker-тест жизненного цикла

Интеграционный тест собирает минимально необходимые образы и использует
временные каталоги/тома. Он выполняет первоначальный запуск, записывает
контрольные данные и секрет, обновляет сервис по другому digest, проверяет
готовность и сохранность, затем моделирует неготовый кандидат и проверяет
возврат к предыдущему digest. Тест не использует рабочие серверные данные и
всегда удаляет контейнеры, сети, тома и временные файлы.

Этот тест выполняется для изменений deploy/Docker/runtime и перед полным
выпуском, но не для документационных или изолированных frontend-изменений.

## Безопасность

- Авторизация GHCR передаётся через stdin во временный Docker config.
- Команды и диагностический JSON не печатают токены, пароли и исходные значения
  защищённых параметров.
- Манифест ссылается на digest и SHA; сервер отклоняет тег без digest.
- Используемый контейнер сканера закрепляется по версии или digest.
- Серверное окружение и каталоги данных находятся вне образа и не
  перезаписываются выпуском.

## Отклонённые варианты

- **Сохранять сборку образа только в GitHub Actions.** Это оставляет выпуск в
  критическом пути полного удалённого набора и не устраняет повторные ожидания.
- **Собирать текущую рабочую копию.** Невозможно надёжно связать образ с Git SHA
  и воспроизвести его.
- **Публиковать multi-arch.** Увеличивает время и поверхность ошибок без второго
  целевого сервера.
- **Развёртывать тег.** Тег изменяем и не доказывает, какой объект фактически
  запущен.
- **Всегда запускать весь CI.** Не даёт дополнительной информации для
  изолированных изменений deploy/docs, но повторяет самые долгие этапы.
- **Полностью отключить последовательный режим Vitest сразу.** Риск скрытого
  общего состояния выше ожидаемой экономии; нужен ограниченный ввод.
- **Удалять все неиспользуемые Docker-объекты.** Общий prune может затронуть
  соседние сервисы и единственный образ отката.

## Последовательность внедрения

1. Зафиксировать контракт проверок и сделать CI учитывающим пути.
2. Ввести ограниченный параллелизм frontend с повторными прогонами.
3. Добавить локальный выпуск и манифест кандидата.
4. Добавить `doctor`, безопасную очистку и отпечатки состояния.
5. Закрепить весь поток Docker-тестом жизненного цикла и обновить runbook.

Каждый этап сохраняет возможность выполнить текущий ручной процесс. Переключение
сервера на новый поток происходит после успешного сквозного теста.
