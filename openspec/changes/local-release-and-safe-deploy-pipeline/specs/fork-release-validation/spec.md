# fork-release-validation Delta

## ADDED Requirements

### Requirement: Быстрый контракт форка защищает собственные точки расширения

Репозиторий SHALL предоставлять одну команду `fork-contract`, которая запускает
быстрые проверки собственных возможностей форка, форматов конфигурации и
границ интеграции с upstream. Команда SHALL завершаться с ненулевым статусом
при нарушении любого включённого контракта и SHALL быть пригодна для локального
запуска и CI.

#### Scenario: локальное изменение нарушает контракт форка

- **GIVEN** изменение ломает поддерживаемую форком границу интеграции
- **WHEN** разработчик запускает `fork-contract`
- **THEN** соответствующая проверка завершается неуспешно
- **AND** команда возвращает ненулевой статус до полной проверки репозитория

### Requirement: Уровень проверки определяется изменениями и относится к одному SHA

Процесс выпуска SHALL выбирать быстрый или полный уровень проверки по
зафиксированным областям изменений. Изменения зависимостей, миграций,
Docker/runtime, общих контрактов или синхронизация upstream SHALL требовать
полного уровня. Оператор MAY явно повысить уровень до полного. Успешный
результат MUST применяться только к точному SHA, на котором он получен.

#### Scenario: изменение только single-host deploy не повторяет runtime-набор

- **GIVEN** после полного успешного runtime-набора изменён только код
  single-host deploy и его тесты
- **WHEN** процесс выбирает проверки нового SHA
- **THEN** он запускает контракт deploy и относящиеся к нему тесты
- **AND** не требует повторного полного frontend/backend-набора

#### Scenario: синхронизация upstream требует полного уровня

- **GIVEN** выбранный SHA включает новые upstream-коммиты
- **WHEN** процесс выбирает уровень проверки
- **THEN** выбирается полный набор
- **AND** его результат привязывается к выбранному SHA

### Requirement: Полный frontend-набор использует проверенный ограниченный параллелизм

Полный frontend-набор SHALL использовать ограниченное число работников после
нескольких успешных повторных прогонов. Тесты с неизолированным общим
состоянием MUST быть исправлены либо явно выделены в последовательную группу.
Сбой повторного прогона MUST блокировать включение новой параллельной
конфигурации.

#### Scenario: изолированные тесты выполняются параллельно

- **GIVEN** frontend-тесты изолируют MSW handlers, таймеры и browser storage
- **WHEN** запускается полный набор
- **THEN** Vitest использует настроенное ограниченное число работников
- **AND** все тесты сохраняют одинаковый результат в повторных прогонах

#### Scenario: тест с общим состоянием остаётся последовательным

- **GIVEN** тестовый набор нельзя безопасно изолировать в рамках изменения
- **WHEN** включается ограниченный параллелизм
- **THEN** этот набор выполняется в явно определённой последовательной группе
- **AND** он не отключает параллелизм для остальных файлов
